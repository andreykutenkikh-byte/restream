# Moblin relay

Эта папка содержит переносимый исходный runtime-пакет. В ней намеренно нет
MediaMTX binary, сгенерированной `slate.mp4`, install manifest и каких-либо
SRT, YouTube или preview credentials. Установщик обязан проверить закреплённые
версии и SHA-256 загружаемых артефактов, а секреты создать непосредственно на
целевом сервере.

Relay использует вертикальный поток 9:16 H.264/AAC. Публичный SRT path
`iphone-live` принимает исходный поток Moblin. Локальный FFmpeg-мост копирует
H.264 без перекодирования, приводит AAC mono/stereo к AAC-LC stereo 48 kHz и
публикует результат во внутренний path `relay-output`. Этот path непрерывно
переключается между LIVE и заставкой и напрямую отправляется штатным forward
MediaMTX в YouTube. Настоящий RTMPS URL и ключ остаются внутри защищённой
конфигурации MediaMTX и не передаются FFmpeg.

Нормализатор работает под небольшим supervisor: перед запуском FFmpeg он
проверяет рост входа через закрытые loopback metrics, а после запуска следит
именно за медиабайтами локального RTMP publisher `relay-output`. Поэтому сетевой
джиттер сначала поглощается SRT-буфером, а после фактической остановки выхода
supervisor быстро освобождает path для заставки. Внешний SRT timeout остаётся
10 секунд и сохраняет соединение при кратком сбое. FFmpeg привязан к жизни
supervisor через Linux parent-death signal, поэтому аварийно осиротевший процесс
не может удержать publisher. Окружение MediaMTX hook перед запуском supervisor
полностью заменяется, поэтому параметры подключения не остаются в `/proc`.

Ожидаемый внешний триггер таких остановок — плохая или пропавшая мобильная
связь. Relay не объявляет протокол SRT неисправным: сначала он автоматически
перезапускает только локальный мост и ждёт восстановления медиабайт в прежнем
соединении. Если тот же точный SRT publisher остаётся формально подключённым, но
медиабайты непрерывно не растут 6 секунд при исправных метриках, сервер
закрывает только это соединение. Это последующая мера восстановления, которая
позволяет работающему Moblin выполнить обычный автоматический reconnect с новым
handshake; вручную перезапускать relay или заново вводить URL не требуется.
Шесть секунд отсчитываются от первого валидного наблюдения неизменившегося
счётчика: уже подтверждённые 2 секунды перед переходом на заставку входят в этот
интервал, если publisher и счётчик не изменились и метрики оставались доступны.

Серверная заставка: 1080x1920, H.264/AVC Main Level 4.0, 30 FPS,
`yuv420p`, GOP 60 (keyframe каждые 2 секунды), AAC-LC stereo 48 kHz,
цикл 12 секунд. Такой же стартовый формат не позволяет YouTube зафиксировать
720p до подключения Moblin. Заставка и тестовый LIVE используют поток без
B-frames, совместимый с low-latency H.264 из Moblin. Исходные закодированные
LIVE-кадры Moblin при этом не перекодируются и не ограничиваются.

## Настройки Media в Moblin

```text
Settings → Streams → профиль → Media
Portrait: ON
Resolution: 1080p (actual output: 1080x1920)
FPS: 30
Codec: H.264/AVC
Bitrate: 8–10 Mbit/s (10 Mbit/s при устойчивом uplink)
Adaptive bitrate: ON
Keyframe interval: 2 seconds
SRT latency: 2000–3000 ms
Local recording: ON
SRT implementation: Official
Big packets: ON
```

В поле URL потока Moblin вводится только защищённый SRT URL из
`sudo relayctl show-moblin-url`. YouTube RTMPS URL и stream key настраиваются
только на сервере через `sudo relayctl configure-youtube`.

Публичный адрес не зашит в `relayctl`. Установщик атомарно создаёт root-owned
`/etc/moblin-relay/node.json` по схеме из `node.json.example`. Обязательное
поле `public_srt_host` принимает IPv4, DNS-имя или IPv6 в квадратных скобках.
`fallback_srt_hosts` — необязательный список (по умолчанию пустой); установщик
не должен угадывать VPN-адрес. Значения `srt_port` и `srt_path` обязаны точно
совпадать с установленным runtime (`8890` и `iphone-live`). Повторный запуск
установщика может обновить только этот не секретный node-файл и не должен
пересоздавать `/etc/moblin-relay/secrets.json`.

После bootstrap `moblin-relay.service` остаётся `inactive` и `disabled`.
Установщик включает только control agent и broker socket. Эфир запускается
вручную после настройки YouTube; это исключает автоматическую отправку в
непроверенный destination при первом запуске или перезагрузке нового сервера.

Входящий SRT listener MediaMTX явно привязан к IPv4 `0.0.0.0:8890` (UDP),
чтобы публичный IPv4 URL из `show-moblin-url` не зависел от системной настройки
IPv6-only sockets.

Первый реальный сеанс Moblin нужно проверить через ffprobe. Входящий AAC может
быть mono: сервер штатно преобразует его в stereo. H.264 profile/level,
разрешение, FPS и GOP должны оставаться совместимыми с заставкой. LIVE-видео
проходит через сервер с `-c:v copy`: разрешение и закодированные видеокадры не
уменьшаются и не перекодируются.

## Диагностика инцидентов

Краткая безопасная хронология за последние шесть часов выводится read-only
командой:

```bash
sudo relayctl incidents
```

Команда просматривает не более 4000 последних записей unit-журнала и выводит
время UTC, этап, стабильный reason code и безопасное описание. Этапы разделены
на `SRT input`, `normalizer`, `relay-output` и `YouTube-forward`; lifecycle самого
unit выводится как `service`. Серии одинаковых FFmpeg-ошибок схлопываются в одну
строку со счётчиком и временем последнего повторения.

Исходный текст journal в этот отчёт не копируется. RTMPS/SRT URL, stream key,
passphrase, publisher password и удалённые адреса не выводятся. Для более низкого
уровня диагностики остаётся `sudo relayctl logs`: он ограничен 200 строками и
также маскирует известные credentials, transport URL и удалённые адреса.

Ключевые причины восстановления:

- `SRT_INPUT_LOST` / `SRT_INPUT_CORRUPT_MEDIA` — вход Moblin пропал или содержит
  повреждённые медиапакеты;
- `NORMALIZER_VERIFIED_STALL` — вход и `relay-output` одновременно перестали
  продвигаться, поэтому watchdog перезапустил FFmpeg;
- `SRT_INPUT_MEDIA_STILL_STALLED` — тот же вход оставался подключённым, но
  медиабайты не возобновились за 6 секунд непрерывного подтверждения, включая
  валидные наблюдения до перехода на заставку;
- `NORMALIZER_OUTPUT_START_TIMEOUT` / `NORMALIZER_CHILD_EXIT` — локальный мост не
  поднял выход вовремя или завершился;
- `NORMALIZER_TIMESTAMP_MISSING` — FFmpeg получил медиапакет без обязательной
  временной метки PTS; это причина сбоя нормализатора, а не диагноз транспорта SRT;
- `SRT_RECOVERY_RESET_REQUESTED` / `SRT_RECOVERY_RESET_SUCCEEDED` — после
  непрерывного 6-секундного отсутствия роста и двух свежих контрольных выборок
  сервер закрыл прежнее транспортное соединение, чтобы работающий Moblin
  автоматически выполнил новый SRT-handshake;
- `SRT_INPUT_ATTACHED` / `SRT_INPUT_DETACHED` — сервер увидел подключение Moblin
  или завершение наблюдения за ним; `DETACHED` рядом с остановкой unit означает
  штатный stop, а во время активного relay — разрыв входного подключения;
- `SRT_INPUT_RESUMED` — после сбоя связи медиабайты снова начали поступать;
  отложенный сброс отменён, сервер продолжает LIVE автоматически;
- `NORMALIZER_BRIDGE_ACTIVE` — после подключения LIVE-медиаданные снова устойчиво
  проходят через нормализатор;
- `SRT_RECOVERY_ATTEMPTS_EXHAUSTED` — исчерпаны ограниченные автоматические
  попытки сброса, требуется операторская диагностика;
- `RELAY_OUTPUT_LOST` — нормализованный поток перестал быть доступен;
- `DELIVERY_TIMESTAMP_REGRESSION` — перед отправкой обнаружена обратная временная
  метка; штатный forward MediaMTX переподключается через 5 секунд с новым
  H.264 timestamp extractor и продолжает с ближайшего keyframe;
- `YOUTUBE_FORWARD_INTERRUPTED` / `YOUTUBE_FORWARD_RETRY` — прервалась либо
  повторяется внешняя отправка.

Совместный stall входа и выхода подтверждается непрерывно не менее 2 секунд
и тремя валидными наблюдениями. Отдельный таймер остановки только выхода равен
2,5 секунды, а непрерывной недоступности метрик — 2 секундам. Короткая пауза
связи или пакетная выдача данных может завершиться в том же процессе FFmpeg,
без лишнего перезапуска и ожидания следующего keyframe. Приёмочный лимит
отсутствия роста downstream capture в native self-test остаётся **3 секунды**;
изменение watchdog-порогов его не ослабляет. Сам по себе `verified-stall`
перезапускает только локальный FFmpeg-мост и не накапливает основание для сброса
соединения. Ошибки запуска, выхода или временной шкалы FFmpeg также не являются
основанием для закрытия SRT. Новый handshake запрашивается только после
6 секунд непрерывного подтверждения, что тот же вход так и не возобновил
передачу, и двух дополнительных неизменившихся выборок непосредственно перед
запросом. Любой рост счётчика немедленно отменяет сброс и возвращает LIVE;
ошибка чтения метрик либо смена UUID полностью обнуляет доказательство и сама по
себе никогда не приводит к закрытию SRT-соединения. Уже доказанная часть
совместного stall переносится в этот шестисекундный интервал; новый полный
интервал после перехода на SLATE не добавляется. Лимиты native self-test не
увеличены.

## Runtime credential для восстановления

Привилегированный renderer создаёт `/run/moblin-relay` с владельцем
`root:moblin-relay` и режимом `0750`. Файлы `mediamtx.json` и `control-api.token`
внутри принадлежат `root:moblin-relay` и имеют режим `0640`: сервис может читать
их, но не изменять. Директива systemd `RuntimeDirectory=` здесь не используется:
она повторно меняла владельца дерева на `User=moblin-relay` после root-renderer,
из-за чего строгая проверка recovery credential отказывала в доступе.

Следующий `ExecStartPre` проверяет credential от настоящего пользователя
`moblin-relay`, до запуска MediaMTX. Успех записывается как
`moblin-relay-normalize:credential-check:ready`. Ошибка содержит только фиксированный
код; `relayctl incidents` переводит его в семейство `RECOVERY_CREDENTIAL_*`:

- `PARENT_OWNER_UNSAFE` / `FILE_OWNER_UNSAFE` — неверный владелец каталога или файла;
- `METADATA_UNSAFE` / `READ_DENIED` — небезопасный тип, режим, группа, число ссылок
  или отсутствие доступа у сервисного пользователя;
- `MISSING` / `METADATA_UNAVAILABLE` / `FILE_CHANGED` / `OVERSIZED` /
  `READ_FAILED` / `FORMAT_INVALID` / `UNAVAILABLE` — остальные ограниченные
  ошибки проверки и чтения.

В журнал не попадают содержимое credential, URL или текст исключения. Renderer
атомарно устанавливает файлы, проверяя владельца и метаданные без следования по
ссылкам. Root `ExecStopPost` удаляет только проверенные runtime-файлы и каталог;
постоянный `/etc/moblin-relay/secrets.json` сохраняется. Unit, renderer и
нормализатор следует обновлять согласованно; возвращать `RuntimeDirectory=` или
ослаблять проверку владельца для обхода ошибки не требуется.

## Локальная история метрик

При установленном native broker история доступна отдельной read-only командой:

```bash
sudo relayctl history
sudo relayctl history --since '2026-09-05T08:00:00Z' --until '2026-09-05T10:00:00Z' --json
```

По умолчанию выводится сводка за последние шесть часов. `--since` и `--until`
принимают ISO-время с явным часовым поясом: `Z` либо смещением, например
`2026-09-05T18:00:00+10:00`. Время без пояса отвергается. `--json` возвращает
точные выборки с UTC Unix timestamp, фиксированными состояниями и числовыми
полями. `--limit` принимает 1–10000, по умолчанию 10000; при превышении остаются
самые новые выборки окна, а `truncated` становится `true`. Для полного экспорта
большого периода разбейте его на более короткие окна.

После запуска `adojapan-relay-broker.service` его отдельный поток собирает
loopback-метрики примерно раз в 5 секунд, независимо от HTTPS heartbeat,
операторских запросов и командной блокировки relay. Нового сервиса нет. Пока
socket-activated broker ещё не запущен либо остановлен, выборки не создаются и
задним числом не восстанавливаются. Сам `relayctl history` только читает уже
накопленные данные и не запускает broker или эфир.

SQLite хранится в `/var/lib/adojapan-relay-history/history.sqlite3`: каталог
`0700 root:root`, база `0600 root:root`, до 7 дней и 120960 строк, с жёстким
пределом базы 64 MiB. Во время записи возможен ограниченный временный rollback
journal. Ошибка чтения или записи истории не прерывает relay и его управление;
ошибка записи даёт только фиксированное сообщение `relay_history_collection_failed`,
не чаще одного раза в минуту.

Сохраняются уникальный и общий входящий SRT bitrate, байты и bitrate локального
RTMP-выхода, исходящие байты и bitrate RTMPS-forward, SRT RTT, счётчики и дельты
принятых, уникальных, потерянных, отброшенных и повторно переданных пакетов,
а также `LIVE` / `SLATE` / `NONE` / `UNKNOWN`. Недостающие метрики, новая сессия,
сброс счётчика, неоднозначный publisher или слишком большой интервал дают
`null` для недоказанных дельт и bitrate. Ноль означает подтверждённое отсутствие
роста в валидном интервале; неизвестные периоды нулями не заполняются. Категории
пакетов могут пересекаться, поэтому их нельзя складывать как независимые потери.

В базу и экспорт не попадают stream key, пароли, URL, IP-адреса, сырые labels
или UUID подключений. YouTube-forward измеряет серверную отправку, а не получение
или воспроизведение видео зрителем. Его счётчик MediaMTX относится к логическому
destination и сохраняется при внутренних retry: замеченные состояния error/idle
сбрасывают базу дельт, но переподключение целиком между двумя опросами не видно.

## Защищённое превью в панели

Превью является необязательным и не влияет на основной relay. Если файла
`/etc/adojapan-relay-agent/preview-reader.token` нет, MediaMTX запускается с
отключённым HLS. Некорректный или небезопасный существующий файл приводит к
отказу запуска, а не к анонимному доступу.

После установки агента и только при остановленных relay и control agent
credential создаётся интерактивной командой:

```bash
sudo adojapan-relay-install-preview-token --generate
```

Значение генерируется локально без вывода секрета; один и тот же защищённый файл читают renderer и агент,
поэтому второго хранилища credential нет. Само значение не передаётся в
аргументах процесса или unit-файле. Файл принадлежит
`restream-agent`, имеет режим `0600`, а runtime-конфигурация содержит только
SHA-256 hash.

При наличии безопасного credential renderer включает только локальный MPEG-TS
HLS:

```text
listener: 127.0.0.1:8888
path: relay-output
variant: mpegts
segment duration: 2s
segment count: 4
reader: relay-preview (read only)
```

Control API включён только на loopback и доступен лишь выделенному recovery-user;
playback и WebRTC отключены. RTSP и RTMP используются только локальным
нормализатором и слушают исключительно `127.0.0.1`; HLS также не
публикуется на внешнем интерфейсе и не требует порта в firewall.
Удаление credential и следующий штатный запуск relay полностью отключают HLS;
основной SRT → YouTube маршрут и его secrets при этом не изменяются.

Проверка исходного renderer без настоящих ключей:

```bash
python3 ./test-render-config.py
```
